What Changed

migration guide revision

The previous version overreached into custom search, filtering, and storefront behavior that the repo does not define safely enough yet.

Bricks-first now Store logic later
Updated direction: the homepage is ready for a Bricks-first migration now, but rego lookup, tyre-size filtering, product-query logic, and checkout behavior are not.

Older assumptions this file now retires

  • A custom tyre-search plugin is required right now.
  • Query filters and full shop/archive build are part of the safe initial migration path.
  • Mock product data and sample pricing belong in the WordPress migration plan.
  • The homepage should be rebuilt primarily through child-theme CSS classes instead of Bricks-native systems.
  • The React checkout, store, and product flows are ready to be reproduced 1:1 in WooCommerce.

Recommended Migration Path

bricks-first workflow

This is the narrow implementation path that matches the current guides and avoids introducing overlapping homepage systems.

  1. Create a normal WordPress page for the homepage and assign it as the static front page.
  2. Build the header and footer as Bricks templates.
  3. Build the homepage sections in Bricks in the same order as App.tsx.
  4. Use the newer repo guides for the homepage, hero, and safe copy-paste sections.
  5. Defer unresolved store, fitment, and filter behavior until the backend approach is actually confirmed.
Inference: if this site is being built in Bricks, do not introduce a competing custom front-page.php for the homepage workflow unless you intentionally want a PHP-template route instead.

WordPress, Bricks, Theme, and Plugin Boundaries

ownership model

Keeping these boundaries clear is what prevents the migration from turning into a mixed Bricks plus custom-template implementation by accident.

Layer Owns Should not own
WordPress core and site config Static front page assignment, page URLs, menus, media library assets Detailed homepage section layout
Bricks Header and footer templates, homepage layout, classes, variables, page settings Custom PHP request handling
Child theme Small enqueued CSS or JS, narrow theme glue, Woo support already present in nonomags-child/functions.php Rego lookup, filter parsing, API integrations
Custom plugin Rego lookup, tyre-size parsing, settings screens, API integrations, shortcode output if needed Whole-page visual layout

Source-backed Notes

wordpress + bricks

These notes summarize the source-backed constraints that shaped the current migration path.

  • WordPress static front page assignment lives in Settings > Reading.
  • front-page.php takes precedence in the WordPress template hierarchy, which is why a competing PHP homepage template can bypass the Bricks page.
  • Bricks 2.3 can convert pasted HTML and CSS into native builder structure, classes, and variables.
  • JavaScript is routed to a Bricks Code element for manual review and signing.
  • Bricks layout defaults should use Section > Container > Block for this homepage.
  • Page metadata and social previews should be set through Bricks Page Settings.
  • Accessibility is part of the baseline build, not a later polish step.
