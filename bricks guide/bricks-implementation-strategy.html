Decision: Use a Bricks-First Homepage Path

The cleanest implementation path is to assign a normal WordPress page as the static front page and build that page in Bricks, with the header and footer also built as Bricks templates.

Recommended path: homepage page in WordPress, homepage layout in Bricks, header/footer as Bricks templates, and no competing custom front-page.php for this workflow.
Official: Static front page Official: Template hierarchy Inference: avoid a competing PHP front page

Why this matters:

  • WordPress supports a static front page in Settings > Reading.
  • front-page.php has precedence in the template hierarchy.
  • Because of that precedence, a separate PHP front-page template can take over the homepage you intended to build in Bricks.

WordPress sources: Create a static front page, Template hierarchy

What The App Actually Contains

Confirmed from src/app/App.tsx:

  • A persistent header and footer frame the whole experience.
  • The default home route is a landing page made of hero, trust, promo, featured products, about, and category sections.
  • The SPA also switches to store, checkout, product:*, and implementation views.
  • The current app relies on client-side state for routes and cart behavior rather than real WordPress URLs or product data.

Bricks Setup Before You Build

  1. Enable Bricks > Settings > Builder > HTML & CSS to Bricks if you want to use the companion snippets.
  2. Use one shared token system for colors, spacing, radii, and buttons instead of ad hoc per-element styling.
  3. Use Bricks-native outer structure: Section, then Container, then Block.
  4. Style the base breakpoint first, then refine smaller breakpoints in responsive editing.
  5. Set homepage metadata and social previews in Bricks Page Settings.
  6. Review performance settings before launch.
Bricks layout default: for this homepage, think in Section > Container > Block and avoid nesting sections inside sections.

Templates vs Components

Use Templates

  • global header
  • global footer
  • hero section only if you expect repeated insert-and-customize use
  • trust, about, or category sections only if you want repeatable section inserts

Use Components

  • trust item
  • category card
  • promo tile
  • button variants or repeated CTA internals
Practical rule: do not turn every repeated block into a component on day one. Use components when synced updates across multiple pages are genuinely useful.

Safe Strategy For The Existing Rego Widget Prototype

The current wordpress-theme/nonomags-child/rego-search.php file is useful, but only as a prototype artifact.

  • It is not a WordPress plugin.
  • It redirects with ?rego= and ?tyre_size= query strings.
  • It does not define how WordPress should parse those values or filter products.
Use it now as: a Bricks UI prototype.
Do not use it now as: finished WordPress search functionality.

If this becomes a real feature later, the safest path is:

  1. Create a dedicated plugin under wp-content/plugins.
  2. Add a proper plugin bootstrap file and header.
  3. Use the Settings API if options or API keys are needed.
  4. Sanitize incoming values and escape output late.
  5. Optionally expose the widget through a shortcode so Bricks can place it cleanly.

Unknowns That Should Stay Unimplemented

  • the rego lookup data source
  • the WordPress-side logic behind ?rego=
  • the WordPress-side logic behind ?tyre_size=
  • the exact shop filtering plugin or query model
  • whether the account icon links to WordPress users, a custom account page, or nothing
  • whether "Mags & Wheels" and "Combos" are categories, archives, or standalone landing pages
  • whether the promo countdown is driven by post meta, options, or manual content updates
Implementation rule: if one of these is still unresolved, leave it out of the build rather than filling the gap with guessed behavior.

What Should Not Be Ported 1:1

  • CartProvider cart state
  • mock product inventory and client-side filtering
  • simulated checkout totals and order confirmation behavior
  • hard-coded related-product logic
  • the implementation route and StyleguidePanel

Recommended Build Sequence

  1. Create the WordPress homepage page and set it as the static front page.
  2. Do not introduce a competing front-page.php while following the Bricks-first homepage path.
  3. Build the global Bricks header and footer templates.
  4. Set up homepage tokens, classes, and page settings in Bricks.
  5. Rebuild the homepage in this order: hero, trust bar, promo shell, featured-products shell, about, category.
  6. Use the companion copy-paste guides where a static section can speed up the build.
  7. Replace placeholder links, images, and temporary copy with real WordPress content.
  8. Defer rego search behavior, product queries, countdown logic, and advanced shop filtering until the backend approach is confirmed.

This sequence is intentionally homepage-first because the homepage is the most presentation-heavy part of the current app and the least dependent on unresolved commerce logic.
